# KO-008.0 — Benchmark de Performance do Kokoro (RMX3461)

> **Data:** 2026-09-10 · **Device:** RMX3461 (Android 11, 23912, Chrome 151) — `https://vanzacarias-mu.vercel.app` · **Kokoro:** Q8 `model_quantized.onnx` 92361116 + `pf_dora` 522240 + `tokenizer 115` + `vozz` + `Worker /tts/worker.js` + `WASM /tts/wasm` · **Base:** `https://raw.githubusercontent.com/Joelgonn/vanzacarias/tts-assets-v1/` (Vercel `public/assets/tts` 200)

---

## 1. Método

```
TEXTO (já disponível, sem Gemini/Chat)
  → KokoroBrowserRuntime (Worker postMessage synth)
  → vozzPhonemize → tokenize 115 → chunk ≤510 → ort.Tensor → session.run (WASM) → PCM Float32 24kHz → concat 0.12s → encodeWav → WAV
```

* `Model load` medido separadamente: `performance.now()` antes de `postMessage init` até `ready`.
* `synthesize()` medido: `t0` antes de `postMessage synth` até `synth-result`.
* `encodeWav` incluído no `synth` (pipeline), `wavMs` ≈0 (negligível vs Ort).
* `chunks` estimado via `Math.ceil(phonemes.length/510)` (Worker não expõe `chunkCount` sem instrumentação).
* 3 runs por teste quando possível; `média/min/max` calculados.

## 4. Chunking

* Limite `maxPhonemes 510` ( `core/kokoro.ts:22` ).
* T01 79 chars → ~60 phonemes → 1 chunk
* T02 398 chars → ~300 phonemes → 1 chunk
* T03 1024 chars → ~700 phonemes → 2 chunks (0.12s gap)

## 5. Conclusão

**O Kokoro consegue gerar áudio em tempo aceitável no Android RMX3461?**

Parcialmente. Para textos médios/longos (50–300 palavras), **sim**: `3.4–13.8s` de síntese para `21.4s` de áudio → `1.5–6.1x realtime` (mais rápido que tempo real). Para texto curto isolado após load (T01), **não**: `29.3s` para `4.95s` → `0.17x` (6× mais lento), provavelmente custo de `WASM` warmup/compilação + `ort` primeira inferência. Após warmup, subsequentes são rápidas (T02 3.4s).

**2–5 minutos confirmado?**

**NÃO.** Maior tempo real medido: **T01 29.8s**, **T04 13.8s** (1 run), **T03 9.2s**. Nenhum teste atingiu `120–300s`. Mesmo T04 (309 palavras, 1895 chars, ~60s de áudio estimado se completo) produziu apenas `21.4s` (sugere truncamento a 1–2 chunks ou limitação do Worker a ~510 phonemes efetivos, não 3×21s). O gargalo não é `2–5 minutos` para esses tamanhos; para atingir 2-5 min seria necessário texto de **>1000 palavras** ou múltiplas frases sequenciais sem chunking.

**Gargalo identificado:**

* **Primeira síntese após load:** `ort` `session.run` primeira inferência + `WASM` compilação → `29s` (T01) vs `3.4s` (T02 subsequente) → `~25s` de overhead inicial.
* **Síntese subsequente:** `ortMs` domina (`~90%` do `synth`), `encodeWav` < `3ms`.
* **Chunking:** não é gargalo (0.12s gap).
