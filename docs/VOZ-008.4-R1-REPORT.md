## C. Existe mismatch?

**SIM — mismatch confirmado em 3 camadas:**

1. **Disco vs Memória (Next):** `.next/BUILD_ID` = `G-U1...` (11:45) **≠** Next `PID 10784` memória (11:26, BUILD_ID antigo, não exposto mas inferido por 404s).
2. **SW vs Servidor:** `public/sw.js` (11:45, `G-U1...`) tenta `fetch` `/_next/static/G-U1.../_buildManifest.js` → servidor retorna 404 (não conhece `G-U1...`).
3. **Caddy vs Next:** `Caddyfile:3 reverse_proxy 127.0.0.1:3000` — Caddy apenas proxy, não serve `.next` direto; 404 vem do Next, não do Caddy (provado por `curl http://127.0.0.1:3000` também 404).

**Onde ocorre:** `self.__SW_MANIFEST` (gerado por `@serwist/next` em build) vs `Next Server` em execução. O `sw.js` é estático em `public/` e atualizado no build, mas o Next server precisa ser **reiniciado** para carregar novo `.next/BUILD_ID` e novos `chunks`. Restart não ocorreu após o build com `NEXT_PUBLIC_VOICE_DEBUG=1` (processos `19000`/`10784` de `11:26`).

## D. O Service Worker está impedindo ou comprometendo o carregamento do build atual?

**SIM.**

- Serwist `precache` usa `handleInstall` que `await` todos `precacheEntries`. Um `bad-precaching-response` (404) **falha a instalação** (`throw` em `el(...)`), e o SW novo fica em `waiting`, não ativa. O SW antigo (sem `NEXT_PUBLIC_VOICE_DEBUG`) permanece `controlling` e serve HTML antigo via `CacheFirst`/`NetworkFirst` handlers.
- Android Chrome mostra SW antigo controlando a página (Application → Service Workers → `public/sw.js` com `BUILD_ID` antigo). O HTML antigo referencia chunks antigos (sem `[VOICE_DEBUG]`), por isso **nenhum `[VOICE_DEBUG]` aparece** mesmo com `console.info` e `Verbose` habilitados.
- Sem SW, `fetch` para `/_next/static` iria direto ao Next e também daria 404 (por mismatch), mas o HTML novo nunca seria servido até Next reiniciar.

**Inconclusivo para transcrição voz:** SW não causa `mic→PCM→Vosk EMPTY` diretamente (Vosk WAV PASS prova Worker funciona), mas **impede a coleta de diagnóstico** e mantém bundle stale sem instrumentação visível.

## E. Isso explica a ausência dos `[VOICE_DEBUG]`?

**SIM.**

- **Cadeia causal:** Build `11:45` com `NEXT_PUBLIC_VOICE_DEBUG=1` → `954` chunk com `return!0` e `[VOICE_DEBUG]` em disco, mas Next `PID 10784` (11:26) não serve esse `BUILD_ID` → `public/sw.js` novo tenta precachear `G-U1...` → 404 → SW install falha → SW antigo permanece → HTML antigo (sem `!0`, sem `[VOICE_DEBUG]`) é servido → `useVoiceInput` antigo sem `console.info` → zero logs mesmo com `TESTE-INFO` funcionando.
- **Prova adicional:** `TESTE-INFO` (`console.info`) funciona porque é `eval` no Console remoto, não depende de bundle. `TESTE-ERROR` também. Já `[VOICE_DEBUG]` ausente prova que **bundle novo não está em execução** no Android, não que `console` está filtrado.

**Status anterior `CONSOLE_FILTERING` (VOZ-008.4) é descartado como causa primária:** `console.info` já é `Info` nível e mesmo assim não aparece, porque o código com `console.info` não está carregado.
