## 1. Alteração Realizada

**Objetivo único:** garantir `AudioContext.state === 'running'` antes do processamento PCM, sem criar contextos desnecessários.

**Ordem corrigida:**

```
getUserMedia
  ↓
AudioContext({sampleRate: ctxRate})
  ↓
if (state !== 'running') await resume()  // captureAudio
  ↓
AudioContext running (verificado, senão erro)
  ↓
VoiceInputController: segundo check stateBeforeCtrl → resume() → running (defesa em segundo nível)
  ↓
createPcmRecorder → recorder.start() → source→processor→destination
  ↓
captura → stop → resample 16k → Vosk
```

## 2. AudioContext — Antes / Depois

### Antes (VOZ-008.4)

- `captureAudio` criava `AudioContext` e retornava imediatamente, sem `resume()`.
- `VoiceInputController.start()` criava `PcmRecorder` e chamava `recorder.start()` sem verificar `state`.
- Em Android Chrome 152, `AudioContext` criado após `getUserMedia` frequentemente fica `suspended` até `resume()` explícito (policy autoplay). `ScriptProcessorNode.onaudioprocess` não dispara em `suspended` → `chunks` vazio → `pcm 0` → `Vosk EMPTY`.
- Evidência: `WAV→Vosk PASS` (offline `decodeAudioData`, não usa `AudioContext` de captura), `mic→PCM→Vosk EMPTY` em realme 48k mono.

### Depois (VOZ-008.5)

- `captureAudio` loga `AUDIOCONTEXT_RESUME` com `stateBefore`, `resumeAttempted`, `stateAfter`, `resumeSucceeded`.
- Se `stateBefore === 'suspended'` (Android), `resumeAttempted=true`, `await resume()`, `stateAfter` deve ser `running`. Se falhar, `CaptureError` → `failCapture` → `error` state, **não envia áudio vazio ao Vosk**.
- `VoiceInputController` adiciona `AUDIOCONTEXT_RESUME_CONTROLLER` como segunda barreira antes de `recorder.start()`.

**Instrumentação preservada:** `[VOICE_DEBUG]` existente mantida. Novos logs `AUDIOCONTEXT_RESUME` e `AUDIOCONTEXT_RESUME_CONTROLLER` apenas com `stateBefore/After`, `resumeAttempted/Succeeded` — sem áudio, sem PII, sem novo sistema de debug.

**Exemplo de logs com `NEXT_PUBLIC_VOICE_DEBUG=1`:**

```
[VOICE_DEBUG] AUDIOCONTEXT_RESUME {stateBefore: "suspended", resumeAttempted: true, stateAfter: "running", resumeSucceeded: true}
[VOICE_DEBUG] AUDIOCONTEXT_RESUME_CONTROLLER {stateBefore: "running", resumeAttempted: false, stateAfter: "running", resumeSucceeded: true}
[VOICE_DEBUG] CAPTURE_START {audioContextState: "running", audioContextSampleRate: 48000, ...}
```

## 5. Conclusão

**Classificação:** `ROOT_CAUSE_CONFIRMED` — `AudioContext suspended` no Android é a causa raiz da captura vazia (`mic→PCM→Vosk EMPTY`), confirmada por auditoria VOZ-008.4-R1 (build/SW) + análise de ciclo de vida `captureAudio` → `PcmRecorder` sem `resume()`.

**Correção:** `ROOT_CAUSE_FIXED` **pendente de validação Android** — código corrigido para garantir `running` antes do PCM, com tratamento de erro que impede `EMPTY` fantasma. Testes automatizados 3 casos PASS, build verde, sem regressão.

**Critério de sucesso (VOZ-008.5):** será `ROOT_CAUSE_FIXED` quando no Android físico:
1. gravação iniciar,
2. `AudioContext` `running` (`AUDIOCONTEXT_RESUME` `stateAfter running`),
3. PCM capturado (`CAPTURE_STOP` `actualSamples >0`),
4. Vosk receber áudio (`VOSK_INPUT` `RMS >0`),
5. `olá` transcrever,
6. frases maiores transcreverem correspondente,
7. sem `EMPTY` sistemático,
8. sem regressão desktop,
9. testes/build verdes (já PASS).

**Se após `resume()` ainda falhar:** usar `[VOICE_DEBUG]` existentes (`CAPTURE_STOP`, `PCM_16K`, `VOSK_INPUT/RESULT`) para classificar entre captura/resampling/Vosk/lifecycle (VOZ-008.5 diagnóstico), sem criar nova auditoria.
