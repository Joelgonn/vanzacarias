## 1. Causa de o Áudio da Pasta estar sendo Utilizado

**Arquivo/linha responsável:** `src/app/dev/voice-test/page.tsx:52` `fixtureRef` único + `340-361` `runTranscribe` com fallback automático para fixture.

**Mecanismo:**

```ts
// Linha 52 (antes): único ref para ambos
const fixtureRef = useRef<{pcm, sampleRate, info} | null>(null);

// Linha 195 (runTestE — microfone): preenchia fixtureRef
fixtureRef.current = {pcm, sampleRate:16000, info: {...}} // PCM de getUserMedia

// Linha 270 (loadFixture — WAV): também preenchia fixtureRef
fixtureRef.current = {pcm, sampleRate:16000, info: {...}} // PCM de fetch('/moonshire.wav')

// Linha 342-361 (runTranscribe — ambos): fallback ambíguo
let pcm = fixtureRef.current?.pcm || null;
let sourceDesc = fixtureRef.current ? 'fixture (E/microfone)' : null;
if (!pcm) {
  // Se microfone não executou E, pcm é null → carrega WAV automaticamente
  const info = await loadFixture(); // fetch('/moonshire.wav')
  pcm = fixtureRef.current?.pcm;
  sourceDesc = `fixture /moonshire.wav ...`;
}
```

**Consequência:** teste de microfone sem `E` (ou com `E` falhado) **automaticamente carregava** `moonshire.wav` e transcrevia o fixture, parecendo que o microfone funcionava quando na verdade era o WAV. Mesmo com `E` executado, `sourceDesc` era ambíguo `'fixture (E/microfone)'`, sem distinção visual, e `runTranscribe` poderia reutilizar PCM de fixture carregado anteriormente se `E` fosse limpo.

**Validações anteriores invalidadas:** todas as 3 validações Android que usaram `G — Transcribe` sem garantir que `E` foi executado imediatamente antes podem ter medido o fixture, não o microfone físico. Por isso `mic→PCM→Vosk EMPTY` real não foi observado.
