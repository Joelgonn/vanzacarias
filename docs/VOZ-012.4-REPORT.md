## 2. Diagnóstico F05 — Reload do modelo a cada remontagem

**Fenômeno:** ao navegar para `/dashboard`, `ChatAssistant` monta → primeira gravação carrega o modelo Vosk (~32MB, worker + WASM) e a resposta demora vários segundos. Ao navegar para outra rota e voltar, o carregamento ocorre **de novo** — idêntico ao primeiro uso.

**Cadeia real encontrada:**
- `useVoiceInput` (hook) limpa o controller no unmount → `controller.dispose()` → `engine.dispose()`.
- `engine.dispose()` em `src/lib/voice/stt/engines/vosk.ts` chamava `disposeVoskModel()` (hard): `model.terminate()` + limpeza do cache module-level (`cachedModel = null`, `cachedModelId = ''`) — o worker morre e o objeto WASM é descartado.
- No close, `loadVoskModel()` re-download/spawna/parseia o modelo inteiro de novo. Na sessão, sem unmount, o cache module-level (`cachedModel`) devolvia a instância já carregada (segunda gravação sem reload) — mas o **unmount matava esse benefício**.
- `ChatAssistant` é montado apenas em `/dashboard` e `/admin/dashboard`: toda navegação fora dessas rotas mata o worker.
- Dahí a latência "primeiro uso" em toda entrada na página.

**Conclusão:** a causa raiz não é o primeiro load (inevitável) — é o **descartes agressivo no unmount** seguido do reload integral no retorno. Nos termos do roteiro: F05 = "evitar demasiadas vezes carregar o modelo" → resolver o ciclo de vida da engine.

## 3. Diagnóstico F06 — Download repetido do modelo no PWA

**Fenômeno:** o modelo é baixado repetidamente em usos futuros, mesmo com service worker registrado.

**Cadeia real encontrada:**
- O worker do vosk-browser baixa o modelo com `fetch('/vosk-model-small-pt-0.3.tar.gz')` — mesmo local de sempre.
- `src/sw.ts` (serwist v9) usa apenas `defaultCache`; **não havia regra dedicada** para o modelo. A regra catch-all `others` (NetworkFirst, cacheName `'others'`, `maxEntries: 32`, 24h) capturava o fetch → não era servido do cache local em usos seguintes.
- O modelo **não podia** ser pré-cacahado no precache: `maximumFileSizeToCacheInBytes: 5242880` (5MB) — o tar.gz tem ~32MB.
- Sem `Cache-Control` longo, o NetworkFirst do `others` voltava à rede com frequência; na prática, re-download integral a cada sessão sem cache válido.

**Conclusão:** faltava uma regra **dedicada, Cache-First e persistente** para o pathname do modelo, colocada **antes** do `defaultCache` (first-match wins), com `cacheName` próprio e versionamento.

## 5. Solução

**F05 — o unmount deixou de matar o modelo:** `engine.dispose()` virou **soft** (`cachedModel = null`; sem `disposeVoskModel()`; o timer keep-warm permanece armado). O modelo permanece vivo em memória (module-level, compartilhado via singleton `STT_ENGINES`) e o retorno à tela reutiliza a mesma instância/worker — **zero novo download/load (~32MB)**. Para não reter memória para sempre, um **TTL de keep-warm** (`10 * 60_000 ms = 10min`, acima do maior guard de inferência F02 ≈ 270s) dispara o hard dispose (`disposeVoskModel()` → terminate + limpeza) após inatividade. Atividade (load ou transcrição) rearma o timer. `terminate()` **não foi removido** — apenas adiado corretamente.

**F06 — o modelo agora tem cache dedicado:** regra **CacheFirst** específica do pathname, posicionada **antes** do `defaultCache` (first-match wins), cache persistente `'vosk-model'` com `ExpirationPlugin` (max 2 entradas / 90 dias / last-used) → segunda utilização volta a servir do cache local mesmo offline. A URL do modelo virou **versionada** (`/vosk-model-small-pt-0.3.tar.gz?v=0.3`): a query é parte do cache key → bump de versão cria entrada nova e o `maxEntries` expurga a antiga; garantido que **nunca** se edita o tar.gz no mesmo pathname mantendo a mesma versão. O servidor devolve `Cache-Control: public, max-age=31536000, immutable` (verificado em runtime) para o pathname, e o header HTTP é statute para o `fetch` do worker dentro do mesmo scope.

## 6. Estratégia de Ciclo de Vida (F05)

```
load()        → loadVoskModel() se não houver instância (1ª vez) ou reutiliza a quente; armWarm()
transcribe()  → transcribeWithVosk (mesma instância); rearma armWarm()
dispose()     → SOFT: cachedModel = null (solta referência), NÃO termina; timer continua armado
timer TTL     → 10 min de inatividade → disposeVoskModel() = terminate() + limpeza (HARD)
```

- Keep-warm rearmado em `load()` e em cada `transcribe()` (atividade real recomeça a contagem).
- TTL maior que o maior guard de inferência possível (270s): um worker mid-flight nunca é derrubado pelo keep-warm.
- `disposeVoskModel()` permanece exportado e é o único caminho de hard cleanup — preservando o contrato de liberar memória.
- Cancelamento/generation/erro/races e gravações consecutivas ficam intactos (cobertos por `voiceControllerVOZ0122` / `voiceLifecycleVOZ012`).

## 7. Estratégia de Cache (F06)

- **Miss:** primeira utilização → fetch do tar.gz → CacheFirst grava em `vosk-model`.
- **Hit:** segunda utilização → mesmo cache key (URL idêntica `?v=0.3`) → servida do cache local (offline incluso).
- **Nunca bate no `defaultCache`:** a regra do modelo é a **primeira** em `runtimeCaching: [VOSK_MODEL_RUNTIME_CACHING, ...defaultCache]`; `isVoskModelRequest` casa só o pathname exato do modelo → nada mais é afetado.
- **Precache:** o tar.gz continua fora do precache (5MB de teto) — a entrada legada no manifest (pré-existentente) não conflita porque o request real leva `?v=0.3` (cache key com query ≠ key do precache) e é conduzido à regra runtime.
- **Limites:** no máximo 2 entradas (versão atual + anterior), 90 dias desde o último uso, depois evicta.

## 13. Evidências de Redução de Load/Download

Medição planejada **exatamente pelo roteiro** (medir sem status, instrumentação por debug já existente) e confirmável nos Testes A–E:

- **Tempo de pré-processamento (1ª vs. subseqüentes):** `VOICE_ENGINE_LOAD` reporta `wasWarmHit` — 1ª `false` (load e spawn), seguintes `true` (queda de vários segundos → ~0 de setup).
- **Número de loads do modelo:** `loadCount` em `getVoskModelStats()` fica em 1 por sessão (antes: 1 por remontagem).
- **Número de downloads/requests (F06):** com o CacheFirst em `vosk-model`, o fetch do modelo deixa de bater na rede em usos seguintes; antes caía no NetworkFirst `others`. O DevTools/Inspect (Network + Cache Storage) prova 1 request de ~32MB na vida do cache, não 1 por sessão.
- **Reuso de cache:** teste E (offline) prova que a segunda utilização se sustenta 100% do cache local.

Resultado esperado: **setup da engine ≈ custo de 1ª utilização; latency percebida cai para transcribe puro nas seguintes; tráfego de rede comprimido para 1 download por versão.**

## 14. Riscos Residuais

- **Memória:** modelo fica em RAM até o keep-warm TTL (10 min de inatividade real). Trade-off deliberado (F05 exige reutilização). TTL rearmado em cada atividade; hard dispose garante liberação após idle. Obs.: no Android o Gerenciador de Tarefas pode encerrar o WebView a qualquer momento (comportamento do SO, não do app) — nesse caso o próximo uso volta a ser 1ª utilização (aceitável, sem loop de cache).
- **Cache vencido/evictado:** 90d de idade ou 2ª versionada → re-download 1×; nunca atualização em lote.
- **Velocidade de 1ª utilização em rede lenta:** o download de ~32MB permanece; mitigado apenas por compressão gzip/br no Nginx/Caddy (documentado, não implementado nesta sprint — ver §15).
- **Header `immutable` em pathname fixo:** seguro porque a URL é versionada via query; troca de modelo exige bump de versão (`VOSK_MODEL_VERSION`) — regra de processo documentada neste relatório (§5/§7).
- **Entrada legada no precache manifest:** não conflita (cache key com `?v=` ≠ precache); permanece inerte.
