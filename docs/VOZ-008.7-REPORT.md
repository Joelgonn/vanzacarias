## 4. Causa

**H1 — timing/finalização do recognizer — CONFIRMADA como causa principal.**

`src/lib/voice/stt/vosk.ts:177-190`:

```ts
recognizer.acceptWaveformFloat(pcm, sampleRate);
acceptEnd = Date.now();
setTimeout(() => {
  afterRetrieve = true;
  retrieveStart = Date.now();
  recognizer.retrieveFinalResult();
}, 100); // espera fixa 100ms
```

- `acceptWaveformFloat(pcm, 16000)` com `pcm.length 110592` envia **todo o áudio de 6.9s de uma vez** ao Worker via `postMessage` (`audioChunk` + `sampleRate`). O Worker (WASM Kaldi) processa de forma **assíncrona**; em Android Chrome 152 com throttling, o tempo entre `acceptWaveformFloat` e `retrieveFinalResult` determina quanto áudio foi decodificado antes do flush final.
- `100ms` é **fixo e curto** para 6.9s de áudio. No fixture de 13.17s, o mesmo `100ms` funcionou porque o áudio do fixture é **contínuo e com alta energia** (sem pausas longas), e o Worker pode ter processado mais rápido em desktop (dev) vs Android (realme mid-range). No áudio real de 6.9s com pausas naturais (`"Olá,"` + pausa + `"quero testar"`), o Worker ainda está em `acceptWaveform` quando `retrieveFinalResult` é chamado, retornando **resultado parcial** (`"olá reconhecimento de voz dele"`).
- O código **ignora** que `acceptWaveformFloat` é assíncrono: `acceptEnd - acceptStart` é ~0-1ms (síncrono), mas `VOSK_RETRIEVE` `acceptToRetrieveMs` é sempre `~100ms`, independente de `durationMs 6912` ou `191824`. O `guard` de 30s (`setTimeout finish(finalText)`) nunca é atingido porque `afterRetrieve` + `result` chega rapidamente com texto parcial, e `finish` resolve com texto truncado.

**Evidência que sustenta:**

- `VOSK_INPUT` 110592 com `rms 0.0456` prova que **todo o PCM chegou ao recognizer** (H2 — perda do último bloco — **descartada**: `actualSamples` 110592 corresponde a `durationMs 6912`, não há `sampleCoverageRatio <1`).
- `VOSK_RESULT` com `wordCount 5` vs esperado 9, `transcriptionLength 28` vs ~45, com `inferenceMs` não reportado mas `acceptToRetrieve 100ms` fixo, indica truncamento por tempo, não por áudio.
- Fixture com mesmo `100ms` passou porque seu `inference` total foi `~13170ms` (RTF 1.10) mas o `retrieveFinalResult` ainda retornou texto completo — diferença pode ser que fixture foi transcrito **logo após load do modelo** (Worker quente) vs mic após `AudioContext` suspend/resume com `interrupted` handling.

**Outras hipóteses descartadas dentro de H1:**

- `retrieveFinalResult` chamado **antes** de todo `acceptWaveformFloat` ser processado → Vosk retorna o que decodificou até 100ms (início da frase + meio), perdendo final (`"em português brasileiro"` → `"dele"` é hallucinação de final truncado).

## 5. Correção Recomendada (para VOZ-008.8)

**Arquivo:** `src/lib/voice/stt/vosk.ts:174-190` — substituir espera fixa por finalização robusta.

**Recomendação mínima (sem AudioWorklet, sem modelo):**

**Opção A (preferida) — chunked feeding + finalização por evento:**

```ts
// Em vez de único acceptWaveformFloat(pcm) + setTimeout 100ms
const chunkSize = 4096; // mesmo de capture, já validado
for (let i = 0; i < pcm.length; i += chunkSize) {
  const chunk = pcm.subarray(i, Math.min(i + chunkSize, pcm.length));
  recognizer.acceptWaveformFloat(chunk, sampleRate);
}
// Após todos os chunks, solicitar final sem delay fixo — Worker já tem todo o áudio
afterRetrieve = true;
retrieveStart = Date.now();
recognizer.retrieveFinalResult();
// Guard de 30s permanece como fallback, mas result final agora tem todo o áudio
```

- **Risco baixo:** mesma API `acceptWaveformFloat`, apenas chunked (documentado `vosk-browser` aceita múltiplos `audioChunk`); preserva `sampleRate`, `grammar`, `resampling`, `AudioContext`.
- **Impacto nos testes:** `vitest` mocks `acceptWaveformFloat` uma vez; precisará mockar múltiplas chamadas ou `expect.any(Float32Array)` com `toHaveBeenCalled` count `ceil(110592/4096)=27`.

**Opção B (alternativa mínima) — aumentar delay fixo:**

```ts
setTimeout(() => { afterRetrieve = true; recognizer.retrieveFinalResult(); }, 500); // 100 → 500ms
```

- **Risco:** ainda fixo, pode falhar para áudio longo em device lento; não resolve causa raiz (assíncrono).

**Opção A é superior:** elimina `setTimeout` fixo, garante que todo `pcm` foi enfileirado antes de `retrieveFinalResult`, e é o padrão usado por `vosk-browser` exemplos (`acceptWaveform` em loop).

**Arquivo e linha exata para VOZ-008.8:**

- `src/lib/voice/stt/vosk.ts:174` — substituir `recognizer.acceptWaveformFloat(pcm, sampleRate);` por loop chunked
- `src/lib/voice/stt/vosk.ts:177-190` — remover `setTimeout 100ms`, chamar `retrieveFinalResult` imediatamente após loop, manter `guard` 30s

**O que NÃO alterar (conforme restrições):** `capture.ts`, `AudioContext`, `resampling`, `ChatAssistant`, `API`, `supabase`, `modelo`, `AudioWorklet`, novo engine.

## 6. O Que NÃO É a Causa

Registrado explicitamente como **descartado** com base em VOZ-008.6 evidência:

- **Silêncio:** `rms 0.0456`, `peak 0.4666`, `samples 110592` — não silencioso
- **Microfone / getUserMedia / MediaStream / AudioContext / resume():** `VOSK_INPUT` com áudio real prova que toda a cadeia até `pcm` está correta; `AudioContext` já corrigido em VOZ-008.5 (`resume` + fallback `interrupted`)
- **Fixture:** `micPcmRef` exclusivo, `handleFalar`/`handleParar` nunca `loadFixture`/`fetch` (validado por `voiceLabSeparation.test.ts` 12 testes)
- **Resampling:** `110592 / 16000 = 6912ms` coerente, `resampleTo16k` 48k→16k com ratio 3.0 já validado em `capture.test` e `voiceController.test` 48k→16k
- **Modelo não carregado:** fixture 191k → 122 chars prova `vosk-model-small-pt-0.3` carregado e Worker WASM funcional no mesmo Android
- **Sample rate / grammar:** `KaldiRecognizer(16000)` sem grammar, `sampleRate 16000` corresponde a `pcm` após resampling

**Causa restante isolada:** finalização do recognizer (`H1`).

## 8. Critério de Conclusão

- Fluxo atual rastreado: **SIM** (`PCM 16k 110592` → `acceptWaveformFloat(pcm)` único → `setTimeout 100ms` → `retrieveFinalResult` → `result` truncado)
- Diferença fixture vs microfone compreendida: **SIM** — fixture 191k com mesmo `100ms` passou, mas mic 110k com pausas naturais truncou; ambos usam mesmo `transcribeWithVosk`, diferença é `timing` vs `conteúdo`, não captura
- Causa confirmada: **SIM** — `H1 timing/finalização` com espera fixa 100ms e envio único de PCM
- Correção objetiva recomendada: **SIM** — `vosk.ts:174` chunked feeding + `retrieveFinalResult` sem delay fixo para VOZ-008.8

**Não considerar `Vosk transcreveu alguma coisa` como resolução** — `5/9` palavras com perda de início e final é **insuficiente** para PT-BR utilizável; objetivo é `8-9/9` palavras com `VOSK_RESULT` completo.
